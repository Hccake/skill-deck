# 测试与验证规范

Skill Deck 需要在 Windows、macOS 和 Linux 上处理文件、启动进程并运行桌面界面，Windows 还涉及 WSL。测试既要尽快发现规则错误，也要覆盖不同操作系统、真实文件系统和桌面运行时中的关键行为。开发者应根据改动内容选择相应测试，并在交付时说明实际运行的平台和尚未验证的场景。

## 测试类型与覆盖范围

测试类型按照实际运行方式划分，各类测试相互补充。使用模拟依赖的测试适合检查规则、接口和异常处理；涉及操作系统或桌面运行时的行为，还需要在对应环境中检查。

| 测试类型 | 适用内容 | 主要检查内容 | 需要另行检查的内容 |
|---|---|---|---|
| 纯规则测试 | 解析、哈希、计划、状态转换和错误映射 | 给定输入能否得到确定结果，领域规则是否成立 | 文件读写、进程、网络和桌面运行时 |
| 接口与契约测试 | 命令输入输出、序列化、窗口命令权限和协议 | 类型是否一致，命令是否注册，权限和错误分类是否正确 | 真实 WebView、目标操作系统和外部服务 |
| 工作流集成测试 | 临时目录、本地 Git 仓库、本地 HTTP 服务和多个模块之间的协作 | 文件读写、冲突处理、失败清理和工作流状态变化 | 其他操作系统、真实 WSL 发行版和桌面窗口协作 |
| 目标平台测试 | Windows、macOS、Linux 的平台分支、加载器、链接和随应用发布的脚本 | 对应操作系统上的编译、进程启动和平台特有行为 | 尚未运行的平台、真实 WebView 和 Windows 与 WSL 之间的完整流程 |
| 桌面应用验收 | 真实 Tauri 应用、插件、WebView、窗口和关键用户流程 | 应用能否启动，桌面运行时中的跨层协作是否正常 | 未执行的外部环境和纯规则的其他输入组合 |

测试名称应与实际运行方式一致。Tauri 模拟运行时（`MockRuntime`）、前端模拟实现（mock）和本地测试服务器不会启动原生 WebView，使用这些能力的测试不属于桌面应用验收。具体限制见 [Tauri 测试说明](https://v2.tauri.app/develop/tests/)。

Rust 单元测试使用 `MockRuntime` 构建 Tauri 应用时，测试夹具只提供被测行为需要的配置和资源。优先使用 Tauri 的测试上下文；确需通过 `generate_context!` 读取应用配置时，使用测试模式，避免测试二进制生成只属于真实应用运行时的资源。

## 选择和编写测试

1. 先确定需要防止的错误、预期结果和需要区分的失败类型，再选择测试类型。
2. 缺陷修复先增加能够复现同一问题的最小测试。完成修复后，确认测试可以识别绕过规则或遗漏异常处理的实现。
3. 解析、状态转换等纯规则优先放在运行快、失败原因清晰的测试中。文件、进程、网络和桌面运行时行为使用相应的真实依赖补充检查。
4. 平台无关的规则在 Windows、macOS 和 Linux 上运行；使用平台 API 或平台特有文件语义的代码在对应操作系统上测试。
5. 测试主动控制时间、并发、网络和环境变量。外部进程、监听端口和临时目录都要设置超时，并在测试结束后完成清理。

### 长期测试的保留标准

长期测试保护稳定的产品行为、公共契约、兼容格式、安全限制或已知缺陷。测试应在这些行为被错误修改时失败，并允许实现结构、组件拆分和视觉细节在行为不变时正常调整。

- 前端行为测试通过可访问名称、可见状态和用户操作观察结果。除设计系统本身的测试外，不断言 Tailwind class、具体 Lucide 图标类名、内部 `data-slot`、固定 grid tracks 或其他组件实现细节；需要检查视觉层级、间距和响应式布局时，使用目标视口下的桌面验收或视觉回归。
- 已完成迁移后，不长期保留“旧字段、旧文案键或旧函数名不得存在”的反向断言。仍需持续禁止的安全字段、敏感信息和领域禁用语应由明确的长期规则、类型约束或专用静态检查维护。
- 薄传输包装器只测试自身增加的行为，例如错误解包、默认参数、参数形态转换和事件 Channel 适配。不为每个类型安全的原样转发函数重复验证调用参数。
- 同一展示 Module 的名称、数量、顺序和状态由该 Module 的 Interface 测试覆盖。父级页面只验证是否正确使用该 Module 以及自身负责的工作流，不重复检查子级图标和布局结构。
- `tauri-specta` 在 debug 应用启动时根据正式命令注册生成 bindings；生成文件进入版本控制。CI 使用普通契约测试在临时目录生成同一内容并与正式文件比较，测试只承担自动判定职责。
- 临时实施约束只在开发过程的 spec 或 ticket 中跟踪。迭代完成时删除仅用于限制迁移步骤、源码组织或中间命名的测试，保留最终行为对应的覆盖。

## 跨平台测试

### 本机路径与 POSIX 路径

本机路径由桌面应用所在的操作系统解释。Rust 代码和测试使用 `Path`、`PathBuf`、`join` 和 `components` 等平台接口构造并比较这类路径。

判断两个本机路径是否相同、是否存在父子关系时，应比较路径组件。业务代码和测试不应通过查找 `/` 或 `\`、替换分隔符或拼接带分隔符的字符串来判断路径关系。需要处理另一操作系统的路径时，应使用明确的解析器或值类型，并在接口处完成本机路径与协议值之间的转换。

WSL、远端 Unix、Git 协议和脚本参数中的 POSIX 路径是协议数据，不使用当前操作系统的 `Path` 规则解释。相关测试需要覆盖根目录、`.`、`..`、绝对路径、相对路径和符号链接目标。

### 条件编译与平台覆盖

`#[cfg(unix)]` 和 `#[cfg(windows)]` 只用于依赖对应操作系统 API、权限或进程能力的代码和测试。解析、协议和业务规则应在所有平台上编译和运行。

平台专属的导入、常量、辅助函数、测试夹具和实现应使用相同的 `cfg` 条件保护，避免其他目标在 `-D warnings` 下出现未使用代码。`#[cfg(test)]` 只表示测试构建会包含这段代码，不能说明它已经在 Windows、macOS 和 Linux 上执行。

新增或修改平台分支后，应在对应操作系统上完成编译、Clippy 和测试。常规 CI 无法覆盖的真实环境检查可以安排在手动验证、定时任务或发布流程中，并在交付说明中记录结果。

### Cargo 测试目标与 Windows 可执行文件

`cargo test` 默认编译并运行库、二进制和集成测试中的测试函数，同时运行文档测试。示例默认参与编译，但不会执行，除非对应目标显式启用测试。每个集成测试文件都会生成独立的测试可执行文件。具体规则见 [Cargo test](https://doc.rust-lang.org/cargo/commands/cargo-test.html) 和 [Cargo targets](https://doc.rust-lang.org/cargo/reference/cargo-targets.html)。

涉及 Windows manifest、Common Controls、动态库、资源文件或原生插件时，完成编译后还要在 Windows 上启动相应的测试可执行文件。窗口、插件和 WebView 之间的协作需要在真实桌面应用中检查。

### Unix Shell 与 WSL

直接执行 `/bin/sh`、依赖 Unix 权限位或 POSIX 系统调用的测试使用 `#[cfg(unix)]`。随应用发布且依赖 GNU 用户态工具的 WSL 脚本，在 Linux 上运行真实脚本测试。

WSL 测试分工如下：

- 跨平台 Rust 测试检查请求、响应、状态转换、协议版本、乱序响应、binary transfer 边界和超时后的迟到响应；
- Linux Engine 测试使用真实临时目录检查 POSIX 大小写、符号链接、权限、执行位、非 UTF-8 路径、读取上限、目录项 identity、物理投影、内容 manifest、单文档条件写入、Library 成员事务与旧事务恢复、目录事务和 lossless lock；
- Linux 测试启动真实 Worker 二进制，检查 handshake、Home 观察、自身摘要、Windows 与 WSL 路径的双向转换、读取调度、control 公平性、Source/Payload handle、双向 binary transfer、单文档写入与冲突保护、Library catalog 与成员提交、Mutation accepted/terminal/ack 顺序、取消清理和关闭；
- ShellCheck 和 Linux 脚本测试检查最小身份 probe 的语法、字段顺序、输入输出和退出状态；测试使用受控 `PATH` 确认 Git 等业务工具不参与 Environment 连接；
- Windows 上连接真实 WSL 2 发行版，检查版本筛选、Worker 准备与部署、`wsl.exe` 数据传输和用户环境。`real_wsl_worker_executes_a_skill_read_plan` 验证读取能力；`wsl_history_round_trip_preserves_unowned_global_fields` 验证单文档条件写入和 lossless lock；`real_wsl2_worker_completes_git_scan_payload_and_release` 使用发行版内的本地 Git fixture 验证 Git、来源扫描、Payload 构建、校验、读取、删除和 Source release；`real_wsl2_worker_executes_and_acknowledges_one_remove_transaction` 验证受保护写入、恢复标记和 acknowledgement 清理。联合门禁默认使用 Ubuntu，也可以通过 `SKILL_DECK_TEST_WSL_DISTRO` 指定发行版，并在成功或失败后清理 WSL 临时目录。
- Worker artifact 测试核对 musl target、manifest、build ID 和实际 SHA-256。Windows debug 构建检查 Tauri resource 目录；NSIS 在一次性 Windows CI runner 中完成静默安装、资源校验和卸载，MSI 通过管理提取检查相同资源。部署测试覆盖首次写入、相同摘要复用、损坏替换、A/B/A 版本切换、非普通目标拒绝和临时文件清理。

跨平台和 Linux 测试无法确认 Windows 与真实 WSL 发行版之间的完整流程。首个业务纵向切片通过联合门禁后，才能批量迁移依赖同一底层能力的调用方。Shell 测试需要捕获标准输出、标准错误和退出状态，设置超时，并在结束后清理子进程与临时目录。用户输入通过位置参数或结构化标准输入传递。ShellCheck 警告作为失败处理；确需忽略时，在代码附近说明原因。

## 测试夹具与外部依赖

### 文件系统与 Git

文件系统工作流使用真实临时目录，并由创建夹具的测试负责清理。测试根据目标平台覆盖目录不存在、目标已存在、悬空链接以及删除链接后保留目标内容等情况。Windows 目录联接（junction）、重解析点（reparse point）和 Unix 符号链接的测试应关注产品行为。只有测试平台适配层本身时，才直接断言操作系统返回的原始字符串或枚举值。

测试使用当前平台的路径接口构造本机路径，JSON、WSL 和其他协议中的 POSIX 路径使用独立表示。依赖当前目录、用户主目录、系统语言、Git 配置或环境变量的测试应显式设置这些条件，并在结束后恢复进程状态。

需要保持字节稳定的 Git 夹具通过 `.gitattributes` 和显式写入控制换行符。哈希测试应说明是否包含可执行权限等元数据；目标平台无法表达某项元数据时，为不同平台分别准备测试样例。平台验收使用对应操作系统原生创建的检出或测试仓库。

### HTTP、时间与外部进程

HTTP 测试使用成熟的本地服务器库，Git 测试使用可控仓库或可替换的传输实现。测试夹具应能稳定产生认证失败、远端引用变化、响应不完整、限流、网络中断、克隆失败和超时等结果。具体重试时间、缓存范围和限流规则由[更新检查](./update-checking.md)及其测试维护。

产品 Module 测试覆盖自定义代理和直接连接。共享 HTTP Transport 使用本地服务器验证 Direct 请求、Custom Proxy 只配置一个代理、设置变更后新请求使用当前设置、客户端默认重定向、总时限、取消和响应读取上限；Discovery URL 契约测试验证 `www.skills.sh` 规范站点及现有公开 `/api/search` 路径。测试不通过修改进程环境重测 reqwest 的 `no_proxy` 行为，也不建立 DNS 公私网分类、地址固定、host allowlist 或请求用途策略。具体响应大小和 Content-Type 由消费内容的产品 Module 测试。这些测试只覆盖应用主动发起的业务请求，不覆盖 WebView 加载的在线图片；连接测试结果也不能证明 WebView 子资源或其他未测试地址可访问。

Git Adapter 测试验证各 Environment 的代理通过单次命令的 `http.proxy` 参数注入，保留原有连接方式或远端未命中代理使用范围时不注入参数，并且任何选择都不会修改持久化 Git 配置。WSL 验收覆盖继承 Windows Git、使用发行版内可访问的独立代理地址和范围，以及保留发行版原有连接方式。测试夹具和日志调用不得主动写入应用持有的认证 Header、密码或 Token；测试不要求生产代码扫描并改写 Git 输出或来源 URL。

时间、随机数、端口和并发完成时机应由测试控制。等待异步结果时，使用通道、带截止时间的等待或测试库提供的同步能力，不通过增加固定等待时间来掩盖竞争问题。

Skill 库条件事务测试需要覆盖同一 Environment 的 I/O 串行化、不同 Environment 的独立执行、当前成员来源记录变化、目录或内容在协调器检查后发生变化、添加与更新的原子替换、移除的原子删除，以及恢复失败后保留证据并阻止后续库读写。进程内 I/O coordinator 测试使用通道和显式通知控制竞争时序；Native Adapter 通过真实临时目录验证 catalog、成员目录和失败回退；WSL 协议测试在 Linux 上执行随应用发布的脚本，并在 Windows 联合验证中覆盖完整提交和恢复。

外部进程测试同时检查退出状态、输出上限、取消、超时和清理。Git 子进程夹具还应分别在标准输出和标准错误中产生超过管道容量的数据，确认进程运行期间持续排空两条管道，并且保留内容不超过诊断上限。超时与取消测试使用可控子进程，检查子进程在截止时间或取消信号到达后被终止并回收。需要检查真实 Git 行为时，使用本地仓库或 `file://` 传输；只检查应用层决策时，使用结果可控的传输实现。

## 后端测试

- 具体产品 Module 的 Interface 是应用行为的主要测试表面；只有外部实现确实存在变化时才建立 seam，单一具体流程直接通过 Runtime Module 和本地可控夹具测试，不为替换测试结果增加生产 Interface；
- 进程内设置校验和内容规则使用纯规则测试；共享 HTTP Transport、Tauri、文件系统、网络和进程依赖放在对应 Adapter 的合同测试中；
- 应用工作流通过真实临时文件系统检查预览、执行、冲突、结果过期、部分失败、清理和错误映射；
- Adapter 测试检查自身负责的协议版本、序列化、错误代码和平台语义，不重复测试上层业务流程。Tauri Updater Adapter 只验证代理映射和一次官方签名或安装委托；取消窗口由 `ApplicationUpdater` Interface 上的应用工作流测试覆盖，不重复测试 endpoint 回退、重定向、下载停滞或官方插件内部状态；
- Rust 命令测试检查命令注册、输入输出和窗口命令权限；生成的前后端类型绑定（bindings）检查用于确认类型已经同步；
- 被忽略的测试应说明运行条件、执行方式和检查内容；其覆盖的风险应通过其他自动化测试或人工验收继续检查；
- Skill 库测试分别覆盖库更新协调器、库内容事务与应用链接事务。协调器接口测试检查来源合并、风险确认、逐项状态变化、取消和部分成功；Skill 目录规划规则测试按物理目录组合直接版本、多个同名库版本、直接 Agent 关联、库 Agent 关联、共享目录、失效链接和无法处理的条目；平台测试检查显式链接、库内容替换与成员删除；工作流测试检查未完成应用、直接安装切换以及 Agent 和项目生命周期保护；
- Environment 本地文档测试确认 JSON 不保存 `EnvironmentRef` 等运行时路由身份，Repository 通过显式 Context 选择 Adapter 和路径；旧开发记录包含多余路由字段时继续读取，后续保存输出最终 schema；
- Scope 版本选举的工作流测试需要连续执行应用库、安装同名直接 Skill、增删直接关联 Agent、保持其他 Agent 使用库版本、调整库顺序、移除直接 Skill 和取消应用库。每一步都检查通用 Skill 目录和全部受影响的 Agent 专用 Skill 目录，确认直接版本只在实际关联的物理目录中优先，并确认重复规划已符合目标的目录时不产生写入；
- 库候选 Source 的合同测试确认它只读取库应用记录、catalog 和真实成员定位信息，不读取 Agent facts 或目标目录；计数型规划夹具确认单个 Scope 在一次业务规划中只构建一份 Agent 目录表；
- `Keep` 执行测试确认无变化目录仍在提交前复核 fingerprint 和可选内容摘要，状态变化时返回过期错误，并且 Native 与 WSL 都不会为纯观察目录创建父目录、替换探针或恢复记录；
- Skill 库删除测试固定点击时的 Environment 和 LibraryId，覆盖删除未选中库后保持当前详情、删除选中库后的 next/previous/empty 选择、权威 snapshot 提交、command failure 就地反馈、详情降级和 committed selection 驱动 URL；
- 共享来源测试覆盖普通来源、`skills add`、Pack、wildcard、显式 Skill 与 Agent 意图，验证安装与库添加使用相同的选择结果、operationId 进度隔离和重试语义；统一来源命令测试覆盖主窗口与安装向导权限、Native 与 WSL 行为、原 operationId 事件和发现会话后续使用；
- Skill 库添加测试固定打开时的 Environment 和 LibraryId，覆盖已有成员不可选、跨主机显式确认、预览过期、执行期间关闭保护、部分失败结果合并和失败项重试。桌面布局使用 `1000 x 760`、`800 x 600` 和最小 `720 x 520` 内容尺寸检查固定 Header、可滚动列表、固定 Footer、长路径和横向溢出；
- 共享测试辅助代码默认相互隔离，每项测试显式控制会影响结果的当前目录、环境变量、时间和外部资源。

## 前端与 Tauri 测试

前端测试从用户能够看到或操作的结果出发，优先通过 `role`、`label`、文本和可见状态定位元素，具体原则见 [Testing Library](https://testing-library.com/docs/guiding-principles)。测试结束时不应留下未处理的 Promise 拒绝或 React `act(...)` 警告。

### 异步状态、定时器与焦点

组件通过状态、ref 回调或 React 提交阶段的 effect 驱动焦点和其他 DOM 副作用。需要在浏览器绘制前完成焦点调整时使用 `useLayoutEffect`。`setTimeout` 只用于产品明确要求的延迟，不用于协调同一次提交中的状态更新、元素挂载和焦点顺序。

测试先触发用户操作，再通过 `act`、`findBy*` 或针对可见结果的 `waitFor` 等待界面更新。产品包含防抖、延迟反馈或超时时，使用 Vitest 受控定时器，并在 `act` 内推进到明确的时间点。增加真实等待时间、反复轮询焦点或放宽超时不能解决竞争问题。

### 对象断言与模块 mock

对象结构本身属于接口约定时，测试应完整比较命令输入输出、持久化格式、协议消息或国际化结构。测试只关心调用方实际使用的部分字段时，使用类型化的部分对象断言，避免无关字段变化破坏调用方测试。

国际化结构测试比较语言包的键和数据形状，关键文案测试精确比较已经确认的文本，组件行为测试只检查当前交互需要的可见内容。

需要保留模块大部分真实行为、只替换少量依赖时，使用 `importOriginal` 创建部分 mock。只有在测试需要隔离整个接口时才使用完整 mock，并提供该接口的全部必需成员。mock 缺少新增成员，说明测试使用的接口没有同步更新；不应在生产代码中增加测试专用分支来绕过问题。

状态模块、Hook 和工作流测试需要覆盖请求标识、过期响应、重复请求、部分完成、错误、重试以及不同操作位置之间的状态隔离。前端测试中模拟 Tauri 调用，只检查调用参数和前端状态变化。Rust 命令测试负责命令注册，bindings 检查负责类型同步，权限测试负责窗口权限；窗口、焦点、插件和 WebView 协作则在真实桌面应用中检查。

## 按改动类型选择验证

| 改动内容 | 应完成的验证 |
|---|---|
| 纯 Rust 或业务规则 | 相关单元测试、格式检查和静态检查；影响公共流程时运行完整 Rust 测试 |
| 文件系统、进程或平台分支 | 在目标操作系统上完成编译、Clippy 和 Rust 测试，并运行相应的文件系统或进程测试 |
| WSL 脚本或协议 | 跨平台协议测试、ShellCheck、Linux 脚本测试，以及 Windows、macOS 和 Linux 上的 Rust 验证；涉及真实发行版时增加 Windows 与 WSL 联合检查 |
| Tauri 命令、bindings 或窗口权限 | 命令测试、权限测试、bindings 检查和相关前端测试；涉及应用启动、插件或窗口时增加桌面应用验收 |
| 操作系统安全存储 | 平台适配层测试和 Windows、macOS、Linux 上的编译检查；在对应桌面平台检查系统凭据库的实际读写 |
| 前端页面、状态或工作流 | 相关组件、状态模块或工作流测试，以及 ESLint 和前端构建；涉及真实 WebView 时增加桌面应用验收 |
| 仓库脚本、CI 或发布策略 | 对应脚本测试、工作流检查和受影响的完整 CI 检查 |

具体命令、当前 CI 任务和发布阶段要求见[贡献指南](../CONTRIBUTING.md)。

## 提交前检查

- 缺陷修复对应的测试在修复前能够复现问题，修复后能够识别错误实现；
- 测试名称与实际运行方式一致，测试结果记录了运行平台、使用的真实依赖和尚未检查的场景；
- 本机路径、POSIX 协议路径、换行符、权限位、链接类型和 Shell 能力均采用与各自语义相符的表示及测试方式；
- 外部资源、时间和并发条件可控，测试失败、超时或中断后不会留下进程、监听端口和临时目录；
- 平台专属实现、导入和测试夹具使用一致的条件编译，并在对应操作系统上完成编译与测试；
- 前端异步测试等待用户可见的结果，对象断言和 mock 范围与测试实际关心的接口一致；
- 交付说明以最新运行结果为准，分别列出编译、自动化测试和桌面应用验收结果，并注明尚未验证的平台或环境。
