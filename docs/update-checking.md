# 更新检查

更新检查用于确认远端来源中的 Skill 是否已经出现新版本，不修改直接安装 Skill 或库成员的内容。检查优先使用远端版本摘要；旧版 Well-known 索引需要下载本次检查成员的内容以计算摘要。用户发起更新后，应用先准备并校验所选内容，再展示确认界面；确认后的执行只消费本次已准备的内容。

Skill 能否更新以及来源失效后的处理方式，见[Skill 生命周期](./skill-lifecycle.md)。lock 文件字段、内容哈希和参考版本规则见[skills CLI 参考与兼容](./skills-cli-reference.md)。

## 检查状态与结果

更新检查记录以下三类信息：

| 信息 | 含义 |
|---|---|
| 能否检查 | Skill 来源和保存的来源记录是否足以获取远端版本信息并完成比较 |
| 上次成功检查的结果 | 上次完成比较后得出的“有更新”或“没有更新” |
| 本次检查状态 | 本次检查是否成功、失败、正在等待重试或因远端服务限流而暂停 |

本次检查失败时，界面会保留上次成功检查的结果，同时提示本次检查未能确认远端状态。只有完成一次版本比较后，才能得出“没有更新”；尚未检查或检查失败都不能表示当前已经是最新版本。

全局、项目和 Skill 库使用相同的版本比较规则。

Skills 页检查所选 Scope 的实际直接安装，支持仅存在于 Agent 专用目录中的 Skill。直接安装记录适配器复用 Agent 目录信息、轻量位置观察和完整库成员归属，确认检查资格；远端比较模块只消费规范化来源记录，不解释 Agent 目录，也不读取安装内容清单。归属无法确认时返回异常。

检查开始时固定所选名称列表。没有来源记录的本地 Skill，以及本地或导入来源不纳入远端检查，也不计入检查异常。来源记录存在但字段不完整或无法解释时，应用显示来源信息异常。

远端请求完成后，应用重新核对实际位置、归属和所选来源记录。相关状态已经变化的 Skill 不接收旧比较；前端按后端提供的比较指纹拒绝失效结果，必要时重新加载位置快照。

Skill 库的检查只处理当前库成员，使用该成员自己的来源记录和版本基线。本地和导入成员不计为检查失败；缺少比较基线的成员无法检查更新，现有内容保留。库成员与同名直接安装 Skill 的比较结果分别归属各自位置。检查结果不作为写入凭据。

两个已有版本标记不相等即视为有更新，包括旧工具采用其他算法生成标记的情况，因此允许一次内容不变的更新。真正缺少标记时不产生比较结论；来源仍可定位时，用户可以按来源重新获取内容。

库检查重试开始时清除旧操作错误，保留仍有效的成功比较。本次失败记录新错误；请求正常返回后清除操作错误，并根据逐来源、逐成员结果显示本次异常。切换库之后，旧请求不能覆盖当前状态。

## 如何获取远端版本信息

Skill Deck 根据 Skill 来源选择获取方式。在 Windows 上，用户选择 Windows 还是 WSL Environment，也会影响由哪个 Environment 执行检查：

- 在桌面应用所在的 Windows、macOS 或 Linux 中，GitHub 来源优先通过 GitHub Trees API 获取完整目录清单和可用于比较的目录树对象 ID（tree object ID）。API 因认证、未授权或仓库不存在、响应信息不完整或来源暂时不可用而无法提供证据时，Skill Deck 改用本机 Git 获取相同的版本信息；
- Windows 用户切换到某个 WSL 发行版后，GitHub 来源改由该发行版中的 Git 获取相同的版本信息；
- GitLab 和普通 Git 来源使用桌面应用所在操作系统或当前 WSL 发行版中的 Git；
- 本地来源没有远端版本可供比较，不发起远端请求；
- Well-known 来源使用索引摘要比较版本。v2 索引直接提供摘要；旧版索引只下载本次检查的直接安装 Skill 或库成员内容，计算兼容摘要，不下载索引中的其他 Skill；
- Well-known 记录同时包含索引地址和安装时摘要时可以检查更新；只有索引地址时不能得出版本比较结果，只有历史制品地址或来源主机时需要先移除当前 Skill，再通过普通安装流程重新添加。
- 完整 Well-known 索引明确不再包含本次检查的 Skill 时，应用显示来源中已不存在，并保留本地内容。成员格式错误、清单不完整或资源下载失败都不表示上游已删除；一个成员失败时，其他有效成员仍可检查。

GitHub Trees API 已确认限流或请求发生普通网络错误时，更新检查继续使用相应的限流等待或来源失败退避，不启动 Git 回退。API 的其他非权威失败进入 Git 回退后，本次结果以 Git 的认证、仓库、`ref`、网络、超时或执行结果为准。

保存的 Well-known 地址遵循[来源范围规则](./skill-lifecycle.md#well-known-与直接下载)：带页面路径的地址只读取对应范围，精确索引保留原有协议、端口、路径大小写及 query。页面或根地址的 query 不转交给生成的索引地址。Native 和 WSL 的已保存 Well-known 更新都保留该来源类型。

已保存的 Git Skill 路径直接在当前来源快照中定位，不受默认发现深度限制。从来源根目录到 Skill 目录的各级路径必须是普通目录；检查和更新不通过目录符号链接或 junction 定位 Skill，即使链接指向来源内部也会拒绝。用户可以调整来源目录结构，或将内容作为本地 Skill 导入。此限制不改变已安装的 Agent 链接、库链接或 Skill 内容内部资源链接的处理规则。

短 ref 名优先解析为分支，明确的分支和标签按原类型解析；附注标签使用其指向的 commit，探测与检出遵循同一规则。来源目录超过内容保留额度时停止获取后的接纳，提示使用较小来源；所选内容无法接纳时提示减少选择，已有准备内容继续受保护。额度与清理规则见[执行与恢复](./execution-and-recovery.md#skill-内容快照)。

这些远端信息只用于判断版本是否变化，缓存失效后仍按上述来源和 Environment 规则重新获取。安装和复制使用经过校验的完整 Skill 内容。

## 网络代理

更新检查沿用“设置 > 代理设置”中的连接方式。HTTP 请求、Native Git 与 WSL Git 分别使用各自当前的配置，执行时的代理选择和配置生效边界见[系统架构](./architecture.md#外部网络访问)。

Skill Deck 自身的应用更新与 Skill 来源更新分别处理。应用更新的插件边界见[系统架构](./architecture.md#外部网络访问)，交互见[产品行为与交互](./product.md#关于与应用更新)，发布资产约束见[贡献指南](../CONTRIBUTING.md#发布与应用更新)。

## 自动检查与手动检查

| 检查方式 | 触发方式 | 行为 |
|---|---|---|
| 自动检查（`Automatic`） | Skill 列表成功加载后由应用发起 | 复用仍在有效期内的远端版本信息；失败后等待规定时间再重试，远端服务限流期间暂停检查 |
| 手动检查（`Force`） | 用户明确要求重新检查 | 可以跳过单个来源因上次失败而设置的等待时间，但远端服务限流期间仍然暂停检查 |

列表加载、切换位置和窗口重新获得焦点时，应用核对当前选择位置的比较基线及新鲜度。仍有效的结果不重复请求；结果过期或基线改变时，自动检查对应成员。搜索和 Agent 筛选只影响展示与手动选择范围。

同一位置、选择、基线和模式的进行中请求共用一次调用。不同选择的手动请求立即提交，可以与自动检查交叠；后端按等价来源合并进行中的获取。前端逐成员按证据观察时间归并比较，按请求编号归并尝试状态，各请求分别结束。检查失败不会通过完成回调立即重新发起请求。

## 缓存、重试与限流

远端版本信息、失败记录和限流信息使用不同的保存范围：

| 记录内容 | 按什么区分 | 如何使用 |
|---|---|---|
| 远端版本信息 | 来源类型、远端主机、仓库或 Well-known 索引，以及分支、标签等 `ref` | 获取成功后一小时内可以复用；GitHub tree ID 和 Well-known 摘要可以跨 Environment 共用，GitLab 与普通 Git 的 CLI 内容哈希只在对应 Environment 内复用 |
| 本地比较结果 | 操作位置、Skill 名称与后端比较指纹 | 基线改变即失效；成员的有效期不因同源其他成员的检查而延长 |
| 单个来源的失败记录 | 桌面应用所在操作系统的用户空间，或 Windows 上当前使用的 WSL 发行版；具体远端来源 | 只限制该位置中对应来源的自动重试，不影响其他位置或来源 |
| 远端服务的限流等待时间 | 桌面应用所在操作系统的用户空间，或 Windows 上当前使用的 WSL 发行版；来源类型和远端主机 | 同时限制该范围内的自动检查和手动检查 |

缓存按照远端来源区分，不按照 Skill 名称区分。名称相同但来源不同的 Skill 不会共用远端版本信息。

界面中的检查状态由位置快照维护。安装、更新或移除成功后，应用清除受影响成员的旧比较，拒绝这些成员在变更前启动的迟到响应；其他成员保留各自结果。来源身份由后端提供，界面不通过显示地址推断来源等价性。

检查失败后的处理分为三类：

1. 认证失败、仓库不存在、分支或标签等 `ref` 不存在，以及无法区分的“不存在或未授权”，都需要用户更新凭据或来源信息。在此之前，自动检查不会重复访问该来源。
2. 网络错误、远端返回的信息不完整或暂时无法访问远端来源时，Skill Deck 会逐步延长下一次自动检查前的等待时间，依次为 `30s -> 1m -> 2m -> 5m -> 10m -> 30m`。检查成功后，等待次数和时间会被清除。
3. GitHub 返回 `429`、带有 `Retry-After` 的 `403`、`X-RateLimit-Remaining: 0`，或者响应正文说明触发 secondary rate limit 时，Skill Deck 会在限流结束前暂停访问同一远端主机。结束时间优先采用 `Retry-After`，其次采用 `X-RateLimit-Reset`；两个响应头都缺失时，等待五分钟。同一客户端在等待期内直接复用该限流结果，不再重复访问 GitHub。

页面已经得知来源目录链接不受支持或来源本身超限时，不自动重复请求同一安装基线。用户调整后可以手动检查；安装基线变化后重新按正常规则判断。

## 何时清除失败和限流记录

以下情况会清除相关失败记录或限流等待时间，使后续检查可以重新进行：

- 检查成功后，清除对应来源的失败次数和等待时间；
- 普通安装改变来源信息后，清除原来源的失败记录；
- GitHub Token 成功保存或清除后，清除桌面应用所在操作系统中 GitHub 的认证失败记录和限流等待时间；
- 本次安装涉及的所有 Skill 都写入成功后，清除相应来源的失败记录。

安装或凭据变更成功后，Skill Deck 会清理相关检查记录。如果清理结果无法写入文件，安装或凭据变更本身仍然有效，界面会另外显示警告。此时内存和文件中的检查记录都保持原值，以免两者不一致。

## GitHub 凭据

用户可以在 Git 设置中连接 GitHub 验证 Token，并将验证通过的 Token 保存到系统安全存储。系统安全存储中的凭据优先于 `GITHUB_TOKEN` 和 `GH_TOKEN`；清除已保存凭据后，Skill Deck 会重新读取环境变量。新的 Token 验证失败时不会覆盖已有凭据；公共仓库因已配置 Token 无效而访问失败时，可以匿名重试一次。

Native Environment 的 GitHub API 回退使用本机 Git 已有的 credential helper、SSH 配置和其他 Git 支持的认证方式。Skill Deck 不从 GitHub CLI 提取 Token，也不为这条回退链路新增凭据存储。WSL Environment 继续直接使用对应发行版中的 Git 及其凭据配置。

系统安全存储不可用时，Skill Deck 不会将 Token 写入明文文件。Token 不会进入全局或项目 lock 文件、更新检查状态文件、前端持久化设置或用户可见诊断。界面只能读取凭据来源、账号、验证结果和额度等不含 Token 的信息。

## 状态文件

更新检查使用带版本号的状态文件，其中包括：

- GitHub、GitLab、Well-known 等来源类型，以及远端主机、仓库、索引和 `ref`；
- 最近获取的远端提交、Skill 相对路径和版本标识；
- 最近一次检查的失败类型、连续失败次数和下次重试时间；
- 远端服务限流的结束时间。

状态文件不会保存 Token、带凭据的来源 URL、原始错误文本或仓库文件内容。写入时采用原子替换。文件内容损坏或结构版本不受支持时，Skill Deck 会隔离原文件并重新创建状态文件，不再沿用其中的记录。清理状态时，Skill Deck 会先写入新文件，再更新内存中的记录；写入失败时，内存和文件都保留原值。
