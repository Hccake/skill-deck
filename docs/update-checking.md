# 更新检查

更新检查用于确认远端来源中的 Skill 是否已经出现新版本。检查时只读取比较版本所需的远端信息，不会把新版本写入 Skill 目录；用户确认更新后，Skill Deck 才会按照已保存的来源获取完整内容并执行安装。

Skill 能否更新、如何重新安装以及如何修复来源，见[Skill 生命周期](./skill-lifecycle.md)。lock 文件字段、内容哈希和参考版本规则见[skills CLI 参考与兼容](./skills-cli-reference.md)。

## 检查状态与结果

更新检查记录以下三类信息：

| 信息 | 含义 |
|---|---|
| 能否检查 | Skill 来源和本地安装记录是否足以获取远端版本信息并完成比较 |
| 上次成功检查的结果 | 上次完成比较后得出的“有更新”或“没有更新” |
| 本次检查状态 | 本次检查是否成功、失败、正在等待重试或因远端服务限流而暂停 |

本次检查失败时，界面会保留上次成功检查的结果，同时提示本次检查未能确认远端状态。只有完成一次版本比较后，才能得出“没有更新”；尚未检查或检查失败都不能表示当前已经是最新版本。

## 如何获取远端版本信息

Skill Deck 根据 Skill 来源选择获取方式。在 Windows 上，用户选择 Windows 还是 WSL Environment，也会影响由哪个 Environment 执行检查：

- 在桌面应用所在的 Windows、macOS 或 Linux 中，GitHub 来源通过 GitHub Trees API 获取完整目录清单和可用于比较的目录树对象 ID（tree object ID）；
- Windows 用户切换到某个 WSL 发行版后，GitHub 来源改由该发行版中的 Git 获取相同的版本信息；
- GitLab 和普通 Git 来源使用桌面应用所在操作系统或当前 WSL 发行版中的 Git；
- 本地来源没有远端版本可供比较，因此不参与更新检查；
- 通过约定地址（Well-known）发现的来源可以重新获取完整内容，但当前没有可用于比较的远端 Git 版本标识，因此更新检查显示“无法比较”。

这些远端信息只用于判断版本是否发生变化。安装、来源修复和复制需要使用经过校验的完整 Skill 内容。缓存失效后，Skill Deck 会在桌面应用所在操作系统中重新获取版本信息；Windows 用户切换到 WSL 后，则会由当前发行版重新获取。

## 网络代理

更新检查沿用“设置 > 代理设置”中的连接方式。桌面应用发起的 GitHub API、Well-known 地址和其他 HTTP 请求使用当前 HTTP 代理路由；Native Git 与 WSL Git 分别按照各自的 Git 代理选项运行。Git 选择“保持原有连接方式”或远端未命中代理使用范围时，应用不注入代理参数。

每次远端请求或 Git 命令在实际执行前读取当前代理设置。应用不注入代理参数时，Git 按已有配置和环境设置连接；应用不会清除或写入用户的持久化 Git 配置。

应用自身的更新检查使用当前 Direct 或 Custom Proxy 设置。Skill Deck 创建官方 Tauri Updater 对象时映射当前设置，插件负责更新清单与安装包请求；已经开始的下载继续使用该对象的连接配置，用户随后保存的新设置供后续更新操作使用。域名解析由官方客户端和所选代理按照各自的标准行为完成。

官方 Tauri updater 插件负责检查版本、下载安装包、验证签名和执行安装。Skill Deck 在插件之外只编排代理映射、进度、取消、超时和诊断。Release 契约要求更新清单不超过 1 MiB、更新器引用的安装包不超过 256 MiB；这些上限用于发现发布产物异常，不构成客户端运行时下载限制。

## 自动检查与手动检查

| 检查方式 | 触发方式 | 行为 |
|---|---|---|
| 自动检查（`Automatic`） | Skill 列表成功加载后由应用发起 | 复用仍在有效期内的远端版本信息；失败后等待规定时间再重试，远端服务限流期间暂停检查 |
| 手动检查（`Force`） | 用户明确要求重新检查 | 可以跳过单个来源因上次失败而设置的等待时间，但远端服务限流期间仍然暂停检查 |

在应用本次运行期间，每个全局或项目位置只会触发一次初始自动检查。重新打开页面、窗口重新获得焦点，或者在已经访问过的位置之间切换，都不会再次触发这项检查。

本地 Skill 状态发生变化后，自动检查只处理新增的可检查 Skill，以及来源、分支或标签等 `ref`、来源仓库内的 Skill 路径（`skillPath`）发生变化的 Skill。Skill Deck 完成安装、更新、来源修复、复制、管理 Agent 或移除后，会同步本次操作涉及的 Skill 状态，避免再次检查所有 Skill。

## 缓存、重试与限流

远端版本信息、失败记录和限流信息使用不同的保存范围：

| 记录内容 | 按什么区分 | 如何使用 |
|---|---|---|
| 远端版本信息 | 来源类型、远端主机、仓库以及分支、标签等 `ref` | 获取成功后一小时内可以复用；同一远端来源的信息可以在 Windows 与 WSL 之间共用 |
| 初始自动检查记录 | 当前全局或项目位置 | 避免在应用本次运行期间重复触发初始检查 |
| 单个来源的失败记录 | 桌面应用所在操作系统的用户空间，或 Windows 上当前使用的 WSL 发行版；具体远端来源 | 只限制该位置中对应来源的自动重试，不影响其他位置或来源 |
| 远端服务的限流等待时间 | 桌面应用所在操作系统的用户空间，或 Windows 上当前使用的 WSL 发行版；来源类型和远端主机 | 同时限制该范围内的自动检查和手动检查 |

缓存按照远端来源区分，不按照 Skill 名称区分。名称相同但来源不同的 Skill 不会共用远端版本信息。

检查失败后的处理分为三类：

1. 认证失败、仓库不存在、分支或标签等 `ref` 不存在，以及无法区分的“不存在或未授权”，都需要用户更新凭据或来源信息。在此之前，自动检查不会重复访问该来源。
2. 网络错误、远端返回的信息不完整或暂时无法访问远端来源时，Skill Deck 会逐步延长下一次自动检查前的等待时间，依次为 `30s -> 1m -> 2m -> 5m -> 10m -> 30m`。检查成功后，等待次数和时间会被清除。
3. GitHub 返回 `429`、带有 `Retry-After` 的 `403`、`X-RateLimit-Remaining: 0`，或者响应正文说明触发 secondary rate limit 时，Skill Deck 会在限流结束前暂停访问同一远端主机。结束时间优先采用 `Retry-After`，其次采用 `X-RateLimit-Reset`；两个响应头都缺失时，等待五分钟。同一客户端在等待期内直接复用该限流结果，不再重复访问 GitHub。

## 何时清除失败和限流记录

以下情况会清除相关失败记录或限流等待时间，使后续检查可以重新进行：

- 检查成功后，清除对应来源的失败次数和等待时间；
- 来源信息发生变化或来源修复成功后，清除原来源的失败记录；
- GitHub Token 成功保存或清除后，清除桌面应用所在操作系统中 GitHub 的认证失败记录和限流等待时间；
- 本次安装涉及的所有 Skill 都写入成功后，清除相应来源的失败记录。

安装或凭据变更成功后，Skill Deck 会清理相关检查记录。如果清理结果无法写入文件，安装或凭据变更本身仍然有效，界面会另外显示警告。此时内存和文件中的检查记录都保持原值，以免两者不一致。

## GitHub 凭据

用户可以在 Git 设置中连接 GitHub 验证 Token，并将验证通过的 Token 保存到系统安全存储。系统安全存储中的凭据优先于 `GITHUB_TOKEN` 和 `GH_TOKEN`；清除已保存凭据后，Skill Deck 会重新读取环境变量。新的 Token 验证失败时不会覆盖已有凭据；公共仓库因已配置 Token 无效而访问失败时，可以匿名重试一次。

系统安全存储不可用时，Skill Deck 不会将 Token 写入明文文件。Token 不会进入全局或项目 lock 文件、更新检查状态文件、前端持久化设置或用户可见诊断。界面只能读取凭据来源、账号、验证结果和额度等不含 Token 的信息。

## 状态文件

更新检查使用带版本号的状态文件，其中包括：

- GitHub、GitLab 等来源类型，以及远端主机、仓库和 `ref`；
- 最近获取的远端提交、Skill 相对路径和版本标识；
- 最近一次检查的失败类型、连续失败次数和下次重试时间；
- 远端服务限流的结束时间。

状态文件不会保存 Token、带凭据的来源 URL、原始错误文本或仓库文件内容。写入时采用原子替换。文件内容损坏或结构版本不受支持时，Skill Deck 会隔离原文件并重新创建状态文件，不再沿用其中的记录。清理状态时，Skill Deck 会先写入新文件，再更新内存中的记录；写入失败时，内存和文件都保留原值。
